## 仕様の解釈として決めたもの（違っていれば直します）

| # | 項目 | 実装した振る舞い |
| --- | --- | --- |
| 13 | 通知の段階を飛ばした場合 | 期限を後から登録したなどで複数の段階が過ぎていたら、最新の段階の通知を1回だけ送る（古い段階をまとめて送らない） |
| 14 | オイルの目安日を過ぎた場合 | 予測日は日々動くため、目安日を過ぎても「当日」の通知は1回送る。残り500km の通知は別に1回 |
| 15 | 車検の満了後 | 通知は送らず、更新を登録するまでホームに警告を出し続ける（5.4） |
| 16 | 通知を許可していない利用者 | 送信済みの記録を残さない（許可した後に、その時点の段階の通知が届く） |
| 17 | フィルターの予測 | 「フィルターも交換した」の記録が1件もない間は予測・通知を出さない（ホームにカードを出さない） |
| 18 | 1kmあたりの維持費 | 期間の合計 ÷ 期間の走行距離。走行距離は「期間開始直前の記録」から「期間内最後の記録」まで。記録が足りなければ「—」 |
| 19 | 月平均 | 今月＝1か月、今年＝1月から今月まで、すべて＝最初の支出の月から今月までの月数で割る |
| 20 | 連携解除後の取り込み済み記録 | 残す（証明付きのまま）。アカウント削除ではすべて消える |
| 21 | Ledra へ渡す「誰が」 | 利用者のアカウントIDではなく、連携ごとの参照ID（`ledra_links.id`）を渡す |
| 22 | 解除の通知が Ledra に届かなかった場合 | こちらの取得を先に止め、通知は1時間ごとに再送する。アカウント削除は解除の通知の成否で止めない |
| 23 | Android の Apple サインイン | ブラウザ経由（Supabase の Apple 設定に Services ID が必要） |
| 24 | 1アカウント1台 | DB のトリガーで上限を強制（プランごとの上限関数 `vehicle_limit`）。データ構造は複数台対応 |
